# State-vector kernel optimizations in the fastest CPU quantum circuit simulators

Scope: how the fastest CPU state-vector simulators apply gates (data layout, index arithmetic, SIMD, threading, special kernels, sampling), plus published performance numbers, aimed at a Rust reimplementation on an i9-14900K (AVX2+FMA, no AVX-512, 24 cores = 8P+16E, 62 GB RAM, 1 NUMA node).

Method note: source code was read directly from shallow clones of the current default branches (Oct 2026): quantumlib/qsim @bdd289e, qulacs/qulacs @6fbf01c, QuEST-Kit/QuEST @a612895 (v4 line), PennyLaneAI/pennylane-lightning @cf9c83b, Qiskit/qiskit-aer @fe964bf. Code links below point to the GitHub `main`/`master` files; line numbers refer to those commits. Papers were read from the arXiv PDFs.

## 1. Memory layout: interleaved (AoS) vs split real/imag (SoA), alignment

### Takeaway
qsim is the only major CPU simulator that stores the state in a SIMD-blocked split layout: 8 real floats followed by 8 imaginary floats per AVX block. Qulacs, QuEST v4, Lightning, and Aer all store interleaved `std::complex<T>`. Aer's AVX2 path de-interleaves into separate real/imag registers on load and re-interleaves on store, so its arithmetic runs on split registers anyway. QuEST v1–v3 used fully separate `real[]`/`imag[]` arrays. A 2025 QuEST optimization study found that moving to AoS alone gave about 1.2× (the paper also says "SoA" elsewhere; see the conflict below). Everyone aligns to 64 bytes.

### Cited Findings
- **qsim (AVX):** the state is "a vectorized sequence of eight real components followed by eight imaginary components. Eight single-precision floating numbers can be loaded into an AVX register" (`StateSpaceAVX<For> : StateSpace<..., float>`). Amplitude `i` sits at float offset `16*(i>>3) + (i&7)` (real) and `+8` (imag). For example, `Sample()` reads `p[16*k + j]` and `p[16*k + 8 + j]` — [qsim lib/statespace_avx.h](https://github.com/quantumlib/qsim/blob/main/lib/statespace_avx.h)
- qsim allocates with `_aligned_malloc(size, 64)` on Windows and `posix_memalign(&p, 64, size)` elsewhere — [qsim lib/vectorspace.h](https://github.com/quantumlib/qsim/blob/main/lib/vectorspace.h)
- The qsim docs say up to 30 qubits fits in about 16 GB of RAM and each extra qubit doubles it. (2^30 × 8 B single-precision complex = 8 GiB for the state; the rest is headroom.) — [qsim docs/overview.md](https://github.com/quantumlib/qsim/blob/main/docs/overview.md)
- **Qulacs:** `using CTYPE = std::complex<double>;`, i.e. interleaved double complex (16 B per amplitude). Its AVX2 kernels use unaligned `_mm256_loadu_pd`/`_mm256_storeu_pd` on `(double*)(state+basis)` — [qulacs src/csim/type.hpp](https://github.com/qulacs/qulacs/blob/main/src/csim/type.hpp), [update_ops_matrix_dense_single.cpp](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_matrix_dense_single.cpp)
- **QuEST v4:** `qcomp* cpuAmps`, with `typedef std::complex<FLOAT_TYPE> qcomp`. Precision is selected at compile time with `QUEST_FLOAT_PRECISION` = 1 (float), 2 (double), or 4 (long double) — [QuEST quest/include/types.h](https://github.com/QuEST-Kit/QuEST/blob/main/quest/include/types.h), [qureg.h](https://github.com/QuEST-Kit/QuEST/blob/main/quest/include/qureg.h), [precision.h](https://github.com/QuEST-Kit/QuEST/blob/main/quest/include/precision.h)
- **QuEST v3.7 (old):** `typedef struct ComplexArray { qreal *real; qreal *imag; } ComplexArray;`, i.e. two separate arrays — [QuEST v3.7.0 QuEST.h](https://raw.githubusercontent.com/QuEST-Kit/QuEST/v3.7.0/QuEST/include/QuEST.h)
- The QuEST v1 paper says the state is 2^n complex numbers in double precision by default (configurable to single or quad), i.e. 16×2^n bytes — [Jones et al., QuEST, arXiv:1802.08032](https://arxiv.org/abs/1802.08032)
- In a 2025 study of QuEST v3.7.0 on a dual Xeon Gold 6230R, "Reordering the data into an AoS alone yields a modest speedup of ∼1.2× over the baseline". Adding AVX2 intrinsics gave about 5× and AVX-512 about 5.5×. AVX-512 + FMA + unroll + prefetch gave about 6× for Hadamard. Inconsistency: the same paper's footnote describes "a 512-bit aligned SoA layout" for the AVX-512 version while the figure legends say AoS — [Low-Level and NUMA-Aware Optimization for High-Performance Quantum Simulation, arXiv:2506.09198](https://arxiv.org/abs/2506.09198)
- That paper also notes that 64-byte alignment is "largely implicit since most simulators use 64-byte alignment for AVX-512 operations" — [arXiv:2506.09198](https://arxiv.org/abs/2506.09198)
- **Qiskit Aer:** `posix_memalign(&data, 64, sizeof(std::complex<data_t>) * data_size)`, i.e. interleaved complex and 64-B aligned — [qiskit-aer src/simulators/statevector/qubitvector.hpp](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qubitvector.hpp)
- Aer's AVX2 kernel `_mm_load_twoarray_complex` loads two interleaved vectors and splits them into separate real and imaginary registers with `_mm256_permute4x64_pd` + `_mm256_blend_pd` (double) or `_mm256_permutevar8x32_ps` + `_mm256_blend_ps` (float). It then does split-register FMA complex arithmetic (`_mm_complex_multiply_add`), and `_mm_store_twoarray_complex` re-interleaves on store — [qiskit-aer qv_avx2.cpp](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qv_avx2.cpp)
- **PennyLane Lightning:** kernels operate on `std::complex<PrecisionT> *arr` (interleaved). The AVX kernels use `permute<swap_real_imag>(v)` within registers to form the cross terms — [GateImplementationsLM.hpp](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/simulators/lightning_qubit/gates/cpu_kernels/GateImplementationsLM.hpp), [avx_common/ApplySingleQubitOp.hpp](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/simulators/lightning_qubit/gates/cpu_kernels/avx_common/ApplySingleQubitOp.hpp)
- The Lightning paper says that with AVX2 (256-bit) or AVX-512 (512-bit), and 64/128 bits per complex number, one register holds "8/4 values for AVX2 or 16/8 for AVX-512 (assuming single/double precision)" — [Asadi et al., Hybrid quantum programming with PennyLane Lightning on HPC platforms, arXiv:2403.02512](https://arxiv.org/abs/2403.02512)
- **Yao.jl:** "Quantum registers store quantum states in contiguous memory" (a Julia `Array{ComplexF64}`, interleaved) — [Luo et al., Yao.jl, arXiv:1912.10877](https://arxiv.org/abs/1912.10877)
- **Häner & Steiger (45-qubit run):** complex double entries are 16 B, and the FMA trick (section 2) uses split-component register duplication — [Häner & Steiger, 0.5 Petabyte Simulation of a 45-Qubit Quantum Circuit, arXiv:1704.01127](https://arxiv.org/abs/1704.01127)
- **qHiPSTER:** complex double with "eight-byte real and eight-byte imaginary" parts, 2^(n+4) bytes total. "We map every two iterations of the inner loop ... to 4-wide SIMD instructions; each iteration, which operates on a complex number composed of real and imaginary parts, is mapped to two entries of the SIMD register" (interleaved AoS in registers) — [Smelyanskiy et al., qHiPSTER, arXiv:1601.07195](https://arxiv.org/abs/1601.07195)

### Inferences
- With the qsim split layout, a generic complex MAC is exactly 4 FMAs on full-width registers, with no shuffles: `rn = fma(rs,ur,rn); in = fma(rs,ui,in); rn = fnma(is,ui,rn); in = fma(is,ur,in)`. Interleaved layouts need `hadd`/`permute` (Qulacs) or de-interleave on load (Aer), which wastes shuffle-port bandwidth. On AVX2, Intel P-cores have only one shuffle port (port 5), so the split layout is the cleaner choice for a new Rust engine. The cost is that amplitude access for I/O and sampling has to go through the `16*(i>>3)+(i&7)` mapping.
- For f32 on AVX2, the natural block is 8 amplitudes = 16 floats = 64 B = one cache line. Use a 64-B aligned allocation, and preferably 2 MiB huge pages for a ≥1 GiB state, to cut TLB misses. Huge pages were not measured in these sources (gap).
- A hybrid choice also works: store interleaved for API simplicity and de-interleave per register as Aer does. The per-load shuffle overhead is hidden when the kernel is memory-bound, which it is for k ≤ 3–4 (section 5).

### Gaps
- I did not inspect Intel-QS, SV-Sim/NWQ-Sim, or Quantum++ source for layout. The Intel-QS paper only shows `QubitRegister<std::complex<double>>` (interleaved) — [Guerreschi et al., Intel-QS, arXiv:2001.10554](https://arxiv.org/abs/2001.10554).
- No head-to-head measurement of split vs interleaved layout under identical kernels was found, apart from the confusingly labelled 1.2× AoS result in arXiv:2506.09198.

## 2. Applying a k-qubit gate: index insertion, iteration order, low vs high qubits

### Takeaway
Every simulator iterates over the 2^(n−k) "base" indices. Each base index gets zeros inserted at the target bit positions, and the 2^k amplitudes at `base | offset(j)` are gathered, multiplied by the matrix, and written back in place.
- **Bit insertion:** qsim and QuEST v4 do the insertion with BMI2 `_pdep_u64(i, ~targetmask)`. Others use shift/mask parity masks.
- **High targets:** qsim splits target qubits into "high" (≥3, i.e. above the 8-lane f32 register) and "low" (0–2, inside the register). For high targets it does plain vector loads at 2^H offsets.
- **Low targets:** the in-register qubits are handled by making 2^L−1 lane-permuted copies of each loaded register (`_mm256_permutevar8x32_ps`) and multiplying by a pre-expanded, lane-varying matrix. This avoids per-FMA shuffles entirely.

### Cited Findings
- **qsim dispatch:** `ApplyGate` switches on `qs.size()` (0–6 qubits; "Assume qs[0] < qs[1] < ..."). If `qs[0] > 2` it uses `ApplyGateH<k>` (all targets high). Otherwise it uses `ApplyGateL<H,L>` with L = number of targets among qubits 0..2, e.g. `ApplyGateL<3,3>` for a 6-qubit gate with 3 low targets. Gates above 6 qubits are "Not implemented" — [qsim lib/simulator_avx.h](https://github.com/quantumlib/qsim/blob/main/lib/simulator_avx.h)
- **qsim high kernel (BMI2 build):** for each outer index `i`, `p0 = rstate + _pdep_u64(i, imaskh)`. Then for k in 0..2^H it does `rs[k] = _mm256_load_ps(p0 + _pdep_u64(k, qmaskh)); is[k] = _mm256_load_ps(p0 + p + 8)`. Each output row is computed with `_mm256_set1_ps` broadcast matrix entries and `fmadd`/`fnmadd`, then stored back to the same addresses (in place). The loop count is `2^(n − 3 − H)` — [qsim simulator_avx.h L337-393](https://github.com/quantumlib/qsim/blob/main/lib/simulator_avx.h)
- **qsim masks:** `GetMasks1` returns `{2 * (~qmaskh ^ ((1 << R) - 1)), 2 * qmaskh}` with R = 3 (log2 of lanes). The "×2" converts amplitude-index bits into float offsets, because each 8-amplitude block is 16 floats. `imaskh` is the inverted mask of high target/control qubits, with the low R bits removed. There is also a non-BMI2 fallback (`#else // __BMI2__`) that builds indices with a loop of shifts and masks (`ii |= i & ms[j]`, `i *= 2`) and a precomputed offset table `xss[1<<H]` — [qsim lib/simulator.h](https://github.com/quantumlib/qsim/blob/main/lib/simulator.h), [simulator_avx.h L808+](https://github.com/quantumlib/qsim/blob/main/lib/simulator_avx.h)
- **qsim low kernel `ApplyGateL<H,L>`:** for each of the 2^H high offsets it loads one register pair, then builds `rs[k2+l] = _mm256_permutevar8x32_ps(rs[k2], idx[l-1])` for l in 1..2^L. That gives 2^(H+L) registers covering all gate-basis inputs per lane. It then does a full 2^(H+L)-term FMA dot product with `w[j]`, a pre-built `__m256` per matrix coefficient that differs per lane. Setup is `FillPermutationIndices<L>(m.qmaskl, idx)` and `FillMatrix<H,L,3>(m.qmaskl, matrix, w)`. `FillMatrix` uses `bits::CompressBits(k, R, qmaskl)` to choose, for each lane k, the matrix element `(j + l) % lsize` — [simulator_avx.h L395-461](https://github.com/quantumlib/qsim/blob/main/lib/simulator_avx.h), [simulator.h L68-98](https://github.com/quantumlib/qsim/blob/main/lib/simulator.h)
- **QuEST v4:** `insertBitsWithMaskedValues(number, bitInds, numBits, bitIndsMask, bitValuesMask)` returns `bitValuesMask | _pdep_u64(number, ~bitIndsMask)` when `QUEST_COMPILE_BMI2`, falling back to a looped `insertBit`. The comment says: "_pdep_u64 scatters number's bits into set-positions of bitIndsMask, hence '~'" — [QuEST quest/src/core/bitwise.hpp](https://github.com/QuEST-Kit/QuEST/blob/main/quest/src/core/bitwise.hpp)
- **QuEST one-target kernel:** `numIts = numAmpsPerNode / 2^(numCtrls+1)`. Each iteration computes `i0 = insertBitsWithMaskedValues(n, sortedQubits, ..., qubitIndMask, qubitStateMask)` and `i1 = flipBit(i0, targ)`, then does a scalar 2×2 complex update. Comment: "the two amplitudes are likely strided and not adjacent (separated by 2^t)". It relies on compiler auto-vectorization, not intrinsics — [QuEST quest/src/cpu/cpu_subroutines.cpp L411-445](https://github.com/QuEST-Kit/QuEST/blob/main/quest/src/cpu/cpu_subroutines.cpp)
- **QuEST any-target dense kernel:** templated on `<NumCtrls, NumTargs, ApplyConj, ApplyTransp>` so loops unroll at compile time. Each thread gets a private `vector<cpu_qcomp> cache(numTargAmps)`. Per iteration it gathers the 2^k amplitudes into the cache with `setBits(i0, targs, numTargBits, j)` and writes back the matrix-vector product. A code comment says precomputing all 2^k masks "curiously ... worsened performance in all regimes!" — [cpu_subroutines.cpp L547-620](https://github.com/QuEST-Kit/QuEST/blob/main/quest/src/cpu/cpu_subroutines.cpp)
- **Qulacs:** `basis_0 = (state_index & mask_low) + ((state_index & mask_high) << 1); basis_1 = basis_0 + mask;` with `mask = 1<<target`, `mask_low = mask-1`, `mask_high = ~mask_low` — [update_ops_matrix_dense_single.cpp](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_matrix_dense_single.cpp)
- **Qulacs paper:** the i-th element of the base set B0 "is computed from the index i in each iteration using bit-wise operation techniques". The 2^m offset list B1 is precomputed. When all targets are high, the B0 loop is unrolled "according to the number of target qubits to enable AVX2's SIMD load/store", because the adjacent memory location is loaded in the next iteration. When a target is low, the elements are already adjacent and are vectorized directly — [Suzuki et al., Qulacs, arXiv:2011.13524 §5.2](https://arxiv.org/abs/2011.13524)
- **Qulacs target-0 special case:** with interleaved double, the 2 amplitudes of a target-0 pair fill one 256-bit register. It uses `_mm256_mul_pd`, `_mm256_hadd_pd`, and `_mm256_permute4x64_pd(x, 216)` to compute both outputs from one load. For targets ≥ 1 it loads `ptr0`/`ptr1` (2 amplitudes each) and uses the hadd-based complex multiply — [update_ops_matrix_dense_single.cpp L118-210](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_matrix_dense_single.cpp)
- **Lightning (LM kernels):** `revWireParity` builds masks from sorted wires: `parity[0] = fillTrailingOnes(w0)`, `parity[i] = fillLeadingOnes(w[i-1]+1) & fillTrailingOnes(w[i])`, and `parity[last] = fillLeadingOnes(w_last+1)`. For a single qubit, `i0 = ((k << 1) & parity_high) | (parity_low & k); i1 = i0 | (1 << rev_wire)`. Lightning numbers wires big-endian (`rev_wire = num_qubits - wire - 1`) — [pennylane_lightning/core/utils/BitUtil.hpp](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/utils/BitUtil.hpp), [GateImplementationsLM.hpp L690-701](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/simulators/lightning_qubit/gates/cpu_kernels/GateImplementationsLM.hpp)
- **Lightning AVX kernels:** each gate has `applyInternal<rev_wire>` (target inside a register, done with compile-time `permute<flip_rev_wire>` / `permute<swap_real_imag>` and diag/off-diag coefficient vectors) and `applyExternal` (target outside the register, two loads `v0`, `v1`). Two-qubit gates need "inter-inter, intra-intra, inter-intra, and intra-inter" variants, and "an arbitrary n-qubit gate we require 2^n functions at the worst case". The authors expect BLAS offload to win "for 4/5 qubits and beyond" — [ApplySingleQubitOp.hpp](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/simulators/lightning_qubit/gates/cpu_kernels/avx_common/ApplySingleQubitOp.hpp), [arXiv:2403.02512 §2.1](https://arxiv.org/abs/2403.02512)
- **Lightning AVX2 kernel selection:** AVX2 kernels are assigned only for states with ≥ 4 qubits (`leq_four = larger_than_equal_to(4)`). They cover PauliX/Y/Z, H, S, T, PhaseShift, RX/RY/RZ, Rot, CZ, CNOT, SWAP, IsingXX, ... — [AssignKernelMap_AVX2.cpp](https://github.com/PennyLaneAI/pennylane-lightning/blob/master/pennylane_lightning/core/simulators/lightning_qubit/gates/AssignKernelMap_AVX2.cpp)
- **Aer:** `index0` inserts zero bits by loop: `lowbits = retval & MASKS[q]; retval >>= q; retval <<= q+1; retval |= lowbits;` over sorted qubits. AVX2 `apply_matrix_avx` is templated on 1..N qubits and also uses `_mm256_permutevar8x32_ps(vreals[i], _MASKS[j-1])` to make lane-permuted copies for low qubits, the same idea as qsim — [qiskit-aer indexes.hpp L212-221](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/indexes.hpp), [qv_avx2.cpp L480-510, L1025+](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qv_avx2.cpp)
- **Häner & Steiger FMA trick:** rewrite the complex MAC as `(ṽR, ṽI) += (vR·mR, vI·mR)` and `(ṽR, ṽI) += (vI·(−mI), vR·mI)`. With `(mR,mR)` and `(−mI,mI)` precomputed, the update "requires only two fused multiply-accumulate instructions instead of several individual multiplications, additions, and permutations". `vl` "can be permuted once upon loading (and then kept in register), as it is re-used for 2^k such complex multiplications". Matrix precomputation is "essentially free" because it is reused 2^(n−k) times. They also use a code generator for k-qubit kernels, register blocking, and instruction reordering — [arXiv:1704.01127 §3.2](https://arxiv.org/abs/1704.01127)
- **Cache associativity hazard for high-order targets:** "Since 2^k values need to be loaded from the state vector (which are at least 2^m apart ...) ... a 2^k-way cache should map the corresponding cache-lines to different locations". Performance drops when 2^k exceeds cache associativity: on Ivy Bridge (8-way L1/L2), k ≤ 3 shows "only a negligible drop", and on KNL the L2 is 16-way. Remapping qubits so that frequently-targeted qubits sit in low bit-locations "allowed for a 2x decrease in time-to-solution" — [arXiv:1704.01127 §3.3, §3.6.2, Figs. 6 & 9](https://arxiv.org/abs/1704.01127)

### Inferences
- **Rust recipe for an AVX2 f32 engine (qsim style):**
  - Use blocks of `[f32;8] re, [f32;8] im`.
  - Sort targets. For high targets, compute `qmaskh` and `imaskh` (excluding the low 3 bits), then per outer index `base = pdep(i, imaskh)` and offsets `pdep(k, qmaskh)` precomputed once into a small table.
  - For low targets (0..2), precompute 2^L−1 `vpermps` index vectors and a lane-expanded matrix `w[]` once per gate.
  - `core::arch::x86_64::_pdep_u64` is available with `target_feature = "bmi2"`. pdep is fast on Intel (Haswell and later) but microcoded and slow on AMD before Zen 3. That is general hardware knowledge, not from these sources.
  - Because the offset table is constant per gate, one pdep per outer iteration is enough. Or iterate in nested loops over the gaps between target bits, as Lightning's parity masks do, which avoids pdep entirely.
- For f64 on AVX2 (4 doubles per register), the "low" qubits are 0–1, and `_mm256_permute4x64_pd` (or `_mm256_permute2f128_pd` + `_mm256_permute_pd`) replaces `vpermps`.
- Keep the matrix in "broadcast" form (`set1` per coefficient, as qsim's H kernel does), or pre-broadcast it into an array of `__m256` (qsim's `w[]`), so the inner loop has no shuffles.
- Associativity: the i9-14900K's P-core L1D is 48 KB 12-way and L2 is 2 MB 16-way (general knowledge, not verified here). By Häner's rule, k ≤ 4 should avoid conflict misses for high targets. Qubit remapping (keeping hot qubits low) is still worthwhile.

### Gaps
- No source quantified pdep vs shift/mask index cost on Intel hybrid cores.
- qsim's `FillControlledMatrixL` (low control qubits inside a register) was seen only by name and signature. Its exact semantics, presumably identity on lanes where the controls don't match, were not fully read.

## 3. Specialized kernels: diagonal, permutation, controlled, 1-qubit, dense k-qubit, measurement collapse

### Takeaway
- **Qulacs, Aer, Lightning, and QuEST** ship many specialized kernels: X/CNOT as pure swaps, diagonal and phase gates as elementwise multiplies, multi-controlled gates that only iterate the controlled subspace, and Pauli-string kernels.
- **qsim** takes the other approach. It has no special-case gate kernels, only dense k-qubit kernels (k ≤ 6) plus controlled variants, and it relies on aggressive gate fusion so that everything becomes a dense 4-qubit-ish matrix.
- **Controlled gates** are cheap everywhere because control bits are folded into the index mask: each control halves the iteration count.
- **Measurement collapse** is a norm reduction plus a renormalize/zero pass.

### Cited Findings
- **Qulacs kernel catalogue:** separate files for `update_ops_named_X/Y/Z/H/CNOT/CZ/SWAP/FusedSWAP`, `matrix_diagonal_single/multi`, `matrix_phase_single`, `matrix_dense_single/double/multi` (with Eigen variants), `control_{single,multi}_target_{single,multi}`, `pauli_single/multi`, `reversible_boolean` (permutation), `qft`, and `projection` — [qulacs src/csim/](https://github.com/qulacs/qulacs/tree/main/src/csim)
- **Qulacs X gate (AVX2):** for target 0 it does an in-register swap with `_mm256_permute4x64_pd` (no arithmetic). Otherwise it loads `ptr0` and `ptr1` and stores them swapped — [update_ops_named_X.cpp L69-97](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_named_X.cpp)
- **Qulacs single-qubit diagonal (AVX2):** a `mul_pd` by two precomputed vectors, then `hadd_pd` — [update_ops_matrix_diagonal_single.cpp](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_matrix_diagonal_single.cpp)
- **Qulacs paper:** "the times for m = 1, 2 are much faster than those for m ≥ 3 ... because specific optimization is performed for dense matrix gates with m = 1, 2. They show almost the same values since the bottleneck ... is ... memory-operation costs." Times for diagonal, Pauli-rotation, and permutation gates "are independent of the number of target qubits m", so "diagonal matrix gates should be used instead of dense matrix gates when the number of target qubits is large". Pauli-X and CNOT "have SIMD optimized functions" and are memory-bound. Timing jumps appear "at 17 and 22 qubits" where the state exceeds cache — [arXiv:2011.13524 §6.1](https://arxiv.org/abs/2011.13524)
- **Qiskit Aer specialized ops:** `apply_mcx`, `apply_mcy`, `apply_mcphase`, `apply_mcu`, `apply_mcswap`, `apply_diagonal_matrix`, `apply_permutation_matrix`, `apply_rotation`, and `apply_pauli`. All run through `apply_lambda` over `indexes(qubits)` — [qubitvector.hpp L236-293](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qubitvector.hpp)
- **QuEST v4 CPU kernels:** `anyCtrlSwap_subA/B/C`, `anyCtrlOneTargDenseMatr`, `anyCtrlTwoTargDenseMatr`, `anyCtrlAnyTargDenseMatr<NumCtrls,NumTargs,...>`, and `anyCtrlAnyTargDiagMatr<NumCtrls,NumTargs,ApplyConj,HasPower>`. Each is parameterized by control count, and "each control qubit halves the needed iterations" — [cpu_subroutines.cpp](https://github.com/QuEST-Kit/QuEST/blob/main/quest/src/cpu/cpu_subroutines.cpp)
- **qsim controlled gates:** `ApplyControlledGate(qs, cqs, cvals, matrix, state)` has variants HH, HL, LH, and LL, by whether the targets and controls are high or low. The high control values are OR'd into the base address: `p0 = rstate + (_pdep_u64(i, imaskh) | cvalsh)`, so only the controlled subspace is touched — [simulator_avx.h L131+, L463-520](https://github.com/quantumlib/qsim/blob/main/lib/simulator_avx.h)
- **qsim gate set:** qsim only has dense-matrix kernels for 1–6 qubits (plus controlled versions) and uses gate fusion. qsimcirq's default `max_fused_gate_size: int = 2`. The docs say for "up to 22 qubits keep f low (2 or 3)" and for 22+ qubits "f=4 is the best option", and that `max_fused_gate_size = 4` "is usually optimal for larger circuits" — [qsim qsimcirq/qsim_simulator.py](https://github.com/quantumlib/qsim/blob/main/qsimcirq/qsim_simulator.py), [docs/choose_hw.md](https://github.com/quantumlib/qsim/blob/main/docs/choose_hw.md)
- **Aer fusion default:** `max_qubit = 5` (`fusion_max_qubit`) — [qiskit-aer src/transpile/fusion.hpp L762](https://github.com/Qiskit/qiskit-aer/blob/main/src/transpile/fusion.hpp)
- **Rollright (Markov et al.):** it "can apply all diagonal gates in a single pass over the wave-function or its slices". It applies "gate clusters on amplitude slices sized to fit in the L2 cache" and "eliminate[s] floating-point multiplications when simulating Google circuits" with AVX2 — [Markov et al., Quantum Supremacy Is Both Closer and Farther than It Appears, arXiv:1807.10749](https://arxiv.org/abs/1807.10749)
- **qHiPSTER controlled-gate behaviour:** at n = 29, controlled-gate time is near the 0.21 s memory bound for high control qubits. With low control-qubit indices it is "suboptimal performance of 0.4 seconds (≈ 2× higher than memory bound)", because only half of each cache line is useful. Performance approaches the bound from control qubit 10 upward — [arXiv:1601.07195 §Single Node Performance](https://arxiv.org/abs/1601.07195)
- **Lightning:** controlled-gate loops are "reduced by a factor 2^(−n) compared with the non-controlled single-qubit gate kernel". It has intrinsic kernels for X, Y, Z, H, S, T, Phase, RX, RY, RZ, Rot, their controlled versions, and Ising gates — [arXiv:2403.02512 §2.1](https://arxiv.org/abs/2403.02512)
- **qsim measurement collapse:** `VirtualMeasure` computes per-thread `PartialNorms`, takes a prefix sum, draws `r`, and selects the thread chunk, then the amplitude. `Collapse` first does a reduction pass: `_mm256_maskload_ps` with a mask from `GetZeroMaskAVX(8*i, mask, bits)`, `fmadd(im,im,re*re)`, and a horizontal sum. A second pass multiplies matching amplitudes by `1/sqrt(norm)` and stores zeros for the rest (the maskload yields 0 for non-matching lanes) — [qsim lib/statespace.h L85-128](https://github.com/quantumlib/qsim/blob/main/lib/statespace.h), [statespace_avx.h L417-449](https://github.com/quantumlib/qsim/blob/main/lib/statespace_avx.h)

### Inferences
- **Recommended kernel set for Rust:**
  1. A generic dense k-qubit kernel (k = 1..5), monomorphized per (H, L) split.
  2. Diagonal kernels for 1..k qubits, applied in one pass. Better still, fuse all consecutive diagonal gates into one diagonal over their union of qubits, as Rollright does.
  3. Permutation kernels (X, CX, SWAP, Toffoli, MCX) as pure loads and stores: no FLOPs, but still a full pass for the touched subspace.
  4. Controls folded into the base mask: `base = pdep(i, free_mask) | ctrl_value_mask`.
- Since every simple kernel is memory-bound (section 5), the biggest win is reducing passes over memory through fusion, not micro-optimizing X vs dense-2×2. Specialized kernels mainly pay off when they reduce bytes moved, e.g. a controlled gate touching 1/2^c of the state, or a diagonal gate fused across many qubits.

### Gaps
- No source gave a measured per-kernel time breakdown, i.e. diagonal vs dense-2×2 vs swap at n = 30 on the same machine. The Qulacs Fig. 2 values exist only as plots.

## 4. Single vs double precision

### Takeaway
qsim's SIMD backends (SSE, AVX, AVX-512) are single-precision only. That halves memory traffic and doubles SIMD width, and it is the main reason qsimcirq tops single-precision benchmarks. Qulacs, Yao, QuEST, Aer, and Lightning default to double. In Qiskit Aer and PennyLane, the single-precision flags were found not to take effect in one benchmark. f32 gives about 7 decimal digits of accuracy, which is adequate for sampling and fidelity estimates. No source quantified drift at depth.

### Cited Findings
- qsim `StateSpaceAVX` is `StateSpace<..., float>`, with "Eight single-precision floating numbers ... loaded into an AVX register" — [qsim lib/statespace_avx.h](https://github.com/quantumlib/qsim/blob/main/lib/statespace_avx.h)
- Jamadagni et al. (2024): "qsimcirq performs best in the large-N limit" among single-precision packages. "For double precision ... qiskit and qpanda are consistently among the fastest packages (qsimcirq only supports single precision)". Their check on a QFT, where the exact ⟨σz⟩ = 0, expects about 7 digits for single and about 16 for double. They "infer that the packages qiskit and pennylane despite promising single precision via an optional setting actually continue to operate in double precision" — [Jamadagni, Läuchli, Hempel, Benchmarking Quantum Computer Simulation Software Packages: State Vector Simulators, arXiv:2401.09076](https://arxiv.org/abs/2401.09076)
- The Qulacs paper's comparison was done in double (128-bit complex). "Since QCGPU and qsim only support simulation with single precision", they were excluded — [arXiv:2011.13524 §7](https://arxiv.org/abs/2011.13524)
- Rollright used `Size of complex : 8 B` (f32) for its 30-qubit 8 GiB run. It reports "Avg inaccuracy per probability > 5.89e-17 (6.32e-06%)" — [arXiv:1807.10749 appendix](https://arxiv.org/abs/1807.10749)
- QuEST: double by default, with single or quad configurable — [arXiv:1802.08032](https://arxiv.org/abs/1802.08032); [precision.h](https://github.com/QuEST-Kit/QuEST/blob/main/quest/include/precision.h)
- Lightning's HPC microbenchmarks "were compiled to use double-precision representations throughout" — [arXiv:2403.02512](https://arxiv.org/abs/2403.02512)

### Inferences
- **Memory:** on 62 GB RAM, f32 allows n = 32 (2^32 × 8 B = 32 GiB), while f64 tops out at n = 31 (32 GiB), with n = 32 at 64 GiB impossible. So f32 buys one extra qubit, and in the bandwidth-bound regime about 2× speed per gate.
- A sensible design is generic over `T: f32 | f64` with f32 as the default, matching qsim. Accumulate reductions (norms, expectation values, sampling cumulative sums) in f64, as qsim's `Sample()` does (it uses `double norm`, `double csum`). Optionally renormalize periodically.

### Gaps
- I found no quantitative study of f32 error growth vs circuit depth (e.g. fidelity loss per 1000 gates) for state-vector simulation.

## 5. Multithreading, memory-bandwidth bound, roofline, hybrid P/E cores

### Takeaway
- **Bound:** state-vector gate application is memory-bandwidth bound. A 1-qubit gate does about 14 FLOP per 16-B (double) amplitude read and written, which is an operational intensity below 0.5 FLOP/B. Fusing into k-qubit gates multiplies the FLOPs by about 2^(k−1) at the same traffic, so k ≈ 4 is the sweet spot where kernels stay memory-bound but do much more work per pass.
- **Threading:** all simulators use OpenMP static, contiguous partitioning of the outer index loop with a size threshold below which they stay serial. qsim uses ≥ 1024 outer iterations, Qulacs ≥ 2^13 amplitudes, and Aer > 14 qubits.
- **Scaling:** it is near-linear until bandwidth saturates. On a single-socket desktop that happens with only a few cores.
- **P/E cores:** no simulator-specific source exists for hybrid cores. Intel's generic OpenMP guidance is to pin to P-cores for predictability.

### Cited Findings
- **Häner & Steiger:** "2·(4[mul] + 2[add]) + 2[add] = 14 FLOP per complex entry of the output state vector. One complex double-precision entry requires 16 bytes ... The operational intensity is therefore less than 1/2, which shows that this application is memory-bandwidth bound on most systems." Also: "as long as the application remains memory bound, larger gates can be applied in (almost) the same amount of time". On Ivy Bridge, "Up to and including k = 4, the kernels are memory bandwidth limited ... k = 4 is the best kernel size to use on this system". On KNL, the "4-qubit gate kernel achieves 1/2 of the MCDRAM bandwidth". Roofline peaks: 230.4 GFLOPS for a 12-core AVX Edison socket and 3133.4 GFLOPS for the 68-core KNL — [arXiv:1704.01127 §3.2-3.3, Figs. 2, 10](https://arxiv.org/abs/1704.01127)
- **Häner threading:** OpenMP with "NUMA-aware initialization". When the outer loop has few iterations, which depends on the target qubits, "The OpenMP collapse directive remedies this problem". On KNL, 4 threads per core worked best for k ≤ 3, and 2 and 1 threads per core for k = 4 and 5 — [arXiv:1704.01127](https://arxiv.org/abs/1704.01127)
- **qHiPSTER bound model:** single-qubit gate time ≥ 2^(m+5)/B_mem. That is 2^(m+4) B of state, times 2 for read and write. For n = 29 (8.5 GB, double) at STREAM B_mem = 40 GB/s per socket, that is 0.43 s per single-qubit gate and 0.21–0.22 s per controlled gate (half the state). "Our single-qubit gate operation runs very close to memory bound, regardless of which qubit the gate is applied to." Gate fusion is used to "block computation in LLC". Hardware: Xeon E5-2680, 8 cores per socket — [arXiv:1601.07195](https://arxiv.org/abs/1601.07195)
- **qsim threading:** `ParallelForT<MIN_SIZE>::Run` uses `#pragma omp parallel` with a manual static contiguous partition: thread m processes `[size*m/n, size*(m+1)/n)`. It runs serially if `size < MIN_SIZE`, and `using ParallelFor = ParallelForT<1024>`. Reductions (`RunReduceP`) keep per-thread partial results in a vector — [qsim lib/parfor.h](https://github.com/quantumlib/qsim/blob/main/lib/parfor.h)
- **Qulacs threading:** `OMPutil::get_inst().set_qulacs_num_threads(dim, 13)` around each gate kernel, and `(dim, 10)` for expectation values. The paper says the OpenMP variant beats serial above "about 14 [qubits] for m = 1, 2 and about 10 for m = 3, 4". On n = 15 the efficiency "saturates around thread number t = 10". On a 2×28-core Xeon Platinum 8276 it saw super-linear speedup at n = 22, where the 67 MB state fits in the 2×~39 MB L3, and efficiency "quickly reduces again" above that once the state no longer fits in cache — [update_ops_matrix_dense_single.cpp](https://github.com/qulacs/qulacs/blob/main/src/csim/update_ops_matrix_dense_single.cpp), [arXiv:2011.13524 §6.4-6.5](https://arxiv.org/abs/2011.13524)
- **Qulacs paper roofline-style model:** T_gate ≈ T_over + max(N_com/V_FLOPS, N_mem/V_BW), approximately. With SIMD and OpenMP enabled, "time for processing arithmetic operations ... becomes smaller than that for processing memory operations" — [arXiv:2011.13524 §5.1, §5.4](https://arxiv.org/abs/2011.13524)
- **Aer:** `omp_threshold_ = 14` ("Qubit threshold for multithreading"), using `#pragma omp parallel for if (num_qubits_ > omp_threshold_ && omp_threads_ > 1)` — [qubitvector.hpp L482, L675](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qubitvector.hpp)
- **Lightning streaming stores:** on Sapphire Rapids (AWS r7i.16xlarge, 32 cores per socket, 30 qubits, double), AVX-512 kernels beat AVX2 and LM up to about 16 threads, but performance saturates at higher thread counts, where "the default multithreaded kernel application gains the lead". `perf c2c` showed cache eviction. Switching `_mm512_store_pd` to `_mm512_stream_pd` (non-temporal) "shows benefit at high-thread counts" but is slower at low counts — [arXiv:2403.02512 §3](https://arxiv.org/abs/2403.02512)
- **QuEST v1:** a single ARCUS-B thread ran ProjectQ 2× faster than QuEST, but QuEST matched or beat it at 16–24 threads. Fig. 5 shows single-node strong scaling on 30-qubit random circuits up to 16 threads — [arXiv:1802.08032](https://arxiv.org/abs/1802.08032)
- **NUMA-aware QuEST (2025):** thread pinning is needed to avoid OS scheduler overhead and migration. Speedup is "near-linear ... until memory bandwidth becomes the bottleneck". Their AVX-512 kernels use an unroll factor of 16 and `_mm_prefetch` at distances of 16 and 32 elements. Headline results: 5.5–6.5× single-qubit, 4.5× two-qubit, 4× RQC, 1.8× QFT vs QuEST v3.7.0, on a dual Xeon Gold 6230R (2×26 cores, HT off) — [arXiv:2506.09198](https://arxiv.org/abs/2506.09198)
- **Intel hybrid guidance (oneMKL, not simulator-specific):** for hybrid Alder Lake-class CPUs, load balancing across core types is hard. Intel suggests running threads on P-cores only (e.g. `KMP_HW_SUBSET=8c:intel_core`, with `,1t` to avoid HT) for predictable performance. If you use both core types, weigh static vs dynamic scheduling and the P:E ratio — [Intel oneMKL Developer Guide: Managing Performance with Heterogeneous Cores](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-linux/2023-1/managing-performance-with-heterogeneous-cores.html)
- **Jamadagni multithreading:** 84 threads (2×22 cores with HT) on Intel nodes shift the onset of exponential scaling by 2–4 qubits. Qiskit and QPanda were fastest for multithreaded RQC at large N — [arXiv:2401.09076](https://arxiv.org/abs/2401.09076)

### Inferences
- **Arithmetic intensity (AI) for a dense k-qubit gate in place**, per amplitude: 2^k complex MACs = 8·2^k FLOP (4 FMAs = 8 FLOP each), and bytes moved = 2·sizeof(complex).
  - f32 (8 B): AI = 8·2^k / 16 = 2^(k−1) FLOP/B → 0.5 (k=1), 1 (k=2), 2 (k=3), 4 (k=4), 8 (k=5).
  - f64: half those values.
- **Ridge point on the i9-14900K:** this needs two specs not verified from a primary source in this research — dual-channel DDR5-5600 at about 89.6 GB/s theoretical (likely ~70–80 GB/s STREAM) and P-core AVX2 FMA peak of 2 FMA × 8 f32 × 2 FLOP = 32 FLOP/cycle/core. 8 P-cores at about 5 GHz then give about 1.3 TFLOP/s f32, and the E-cores add roughly 16 × 16 FLOP/cycle at about 4 GHz ≈ 1 TFLOP/s. The ridge is therefore about 2.3e12 / 8e10 ≈ 25–30 FLOP/B. All k ≤ 5 kernels are firmly memory-bound on this machine, so fusing up to k = 5 is nearly free in compute. The practical limit becomes the L1 register/associativity constraint (32 values per gate block, 16 YMM registers) rather than FLOPs. Treat this as an estimate to verify with STREAM.
- **Expected per-gate time at n = 30:** f32 is 8 GiB; one read+write pass moves 17.2 GB, so ≈ 0.22–0.25 s at 70–80 GB/s. f64 takes ≈ 0.45–0.5 s per pass. This is consistent with qHiPSTER's 0.43 s for a 29-qubit f64 gate at 40 GB/s. So total circuit time ≈ (#fused passes) × 0.23 s, and fusion quality is the dominant lever.
- **Threading on a 14900K:** a few P-cores probably saturate DDR5 bandwidth for streaming kernels. E-cores add little for k ≤ 2 kernels but may help for k = 4–5 fused gates, which are more compute-heavy. With static equal-size partitioning, slower E-cores become stragglers. Prefer either P-core pinning, or dynamic/guided chunking with chunks sized to the L2 (≥ 64–256 KB per chunk) to avoid false sharing and give load balance. qsim's contiguous static partition never false-shares, because chunks are huge and contiguous.
- Non-temporal (streaming) stores are worth testing only when the state is much larger than the LLC (36 MB on the 14900K). For in-place updates they skip the read-for-ownership, which Lightning saw helping at high thread counts.

### Gaps
- No simulator paper or repo measured performance on Intel hybrid (P/E) CPUs. The Intel guidance is generic (oneMKL).
- No published roofline for Raptor Lake specifically. The i9-14900K bandwidth and FLOP figures above are general-knowledge estimates that should be measured (STREAM triad, likwid-bench).

## 6. Published throughput / benchmark numbers

### Takeaway
Absolute per-gate numbers in the literature are scattered and hardware-dependent. The consistent picture:
- At n ≈ 29–30, a single-qubit gate costs about 0.2–0.5 s on a socket-class machine and is memory-bound.
- qsim (f32, fused) is fastest in single precision.
- Qiskit Aer and QPanda are fastest among double-precision CPU packages at large N.
- Qulacs, Yao, and ProjectQ converge to the same memory-bound speed for n > 20 on single gates.
- Yao and Qrack have the lowest small-N overhead.

### Cited Findings
- **qHiPSTER:** n = 29 (single socket, 8.5 GB double), 40 GB/s STREAM gives a 0.43 s memory bound per 1-qubit gate and 0.21 s per controlled gate. The measured 1-qubit gate is "very close to memory bound". A 40-qubit distributed run took 0.43 s / 0.21 s for gates without communication — [arXiv:1601.07195](https://arxiv.org/abs/1601.07195)
- **Rollright (Markov et al. 2018):** a 30-qubit, depth 1+26+1 Google circuit (524 gates, 161 two-qubit) ran in 71 s on a MacBook Pro i7-7700HQ (4 cores / 8 threads, AVX2, 8 B complex, 8 GiB state). That averages about 0.135 s per gate, with diagonal gate passes merged and L2-sized gate clusters. 55.7% of the time (39.5 s) went to X/Y/H gates on high qubits — [arXiv:1807.10749](https://arxiv.org/abs/1807.10749)
- **Qulacs paper:** benchmarks on 2× Xeon Platinum 8276 (28 cores each, 2.2 GHz) for per-gate data and 2× Xeon E5-2687W v4 (24 cores total) for circuit comparisons, double precision. "Qulacs is one of the fastest simulators" for random circuits. With circuit optimization, Qiskit Aer can beat Qulacs without it. Results are in figures only. The GPU variant has about 10 µs overhead per gate — [arXiv:2011.13524 §6-7](https://arxiv.org/abs/2011.13524); benchmark code at [qulacs/benchmark-qulacs](https://github.com/qulacs/benchmark-qulacs)
- **Yao.jl paper:** single-gate benchmarks (X, H, CNOT, Toffoli on qubit 2, n = 4–25) on a Xeon Gold 6230. "Yao, ProjectQ, and qulacs reach similar performance when the number of qubits n > 20. They are at least several times faster than other packages ... suggests that they all reached the top performance for this type of full amplitude classical simulation on CPU." Values are plotted in ns, not tabulated — [arXiv:1912.10877 §5](https://arxiv.org/abs/1912.10877)
- **Jamadagni et al. 2024:** tasks were Heisenberg dynamics, RQC, and QFT, on 2×22-core Intel nodes with a 300 GB memory limit; multithreaded runs used 84 threads. Single-precision single-thread: qsimcirq is fastest at large N, and hybridq "almost competes with qsimcirq for large N". Double: qiskit and qpanda are fastest. Below N ~ 15, yao and qrack have the least overhead. The interactive data explorer is at qucos.qchub.ch — [arXiv:2401.09076](https://arxiv.org/abs/2401.09076)
- **Lightning (30 qubits, double, Sapphire Rapids r7i.16xlarge):** AVX-512 > AVX2 > LM for 1, 4, and 16 threads, while LM leads at higher thread counts. Results are in plots — [arXiv:2403.02512](https://arxiv.org/abs/2403.02512)
- **NUMA-aware QuEST (2025, 2× Xeon Gold 6230R):** Hadamard on qubit 2 for n = 23–35 is about 6× faster than QuEST v3.7.0 with AVX-512 + FMA + unroll + prefetch, and about 5× with AVX2 intrinsics alone. Cited prior work: HpQC (AVX2/FMA) averaged a 2.20× speedup over QuEST on QFT — [arXiv:2506.09198](https://arxiv.org/abs/2506.09198)
- **Häner & Steiger (KNL / Edison):** 4-qubit kernels reach about 1/2 of MCDRAM bandwidth, about 2× DDR. A 45-qubit run used 8,192 KNL nodes, 0.5 PB. A 36-qubit, depth-25 circuit (6×6, 447 gates) took 28.92 s on 64 nodes, 12.8× faster than prior work — [arXiv:1704.01127](https://arxiv.org/abs/1704.01127)
- **Intel-QS:** strong scaling of 1-qubit gates on a 32-qubit state across 32–512 MPI ranks on SuperMUC-NG (2× Xeon Platinum 8174, 24 cores per socket), and weak scaling from 32 to 42 qubits. Results are in figures — [arXiv:2001.10554](https://arxiv.org/abs/2001.10554)
- **SV-Sim (SC21):** PGAS-based. The single-device approach uses "device functional pointers" for gates across CPUs, GPUs, and Xeon Phi, with "gate-specialized implementation" exploiting sparsity and identity structure. The evaluation is mostly GPU (A100/V100/MI100, Summit, Theta) — [PNNL SV-Sim](https://github.com/pnnl/SV-Sim); [SC21 paper DOI 10.1145/3458817.3476169](https://www.doi.org/10.1145/3458817.3476169)

### Inferences
- A good target for a Rust engine on the 14900K at n = 30 (f32) is about 0.25 s per full-state pass, i.e. close to STREAM bandwidth. With qsim-style fusion (f = 4–5) that should beat qsim per gate, given that qsim already sits near this bound.
- A depth-20 random circuit with about 600 gates at n = 30 that fuses into about 100–150 passes would take roughly 25–40 s. This is an extrapolation from the bandwidth math, not a measurement.

### Gaps
- I found no clean table of "time per gate at n = 30" for qsim, Qulacs, Aer, QuEST, Lightning, and Yao on the same CPU. The comparison papers (Qulacs, Yao, Jamadagni, Lightning) give results mostly as plots. Jamadagni's numeric data is in their online explorer, which I did not fetch.
- The Mandrà et al. benchmark and the qsim-specific CPU benchmark tables were not located. The qsim docs now publish only GPU (cuQuantum) timings.

## 7. Measurement, sampling, and Pauli expectation values

### Takeaway
- **Many shots (qsim):** draw S uniforms, sort them, and sweep the cumulative |amp|² once. That is O(2^n + S log S), with one pass over memory regardless of S.
- **Many shots (Aer):** build a coarse prefix-sum index of 2^10 blocks, then for each shot scan the blocks and then within one block.
- **Pauli strings:** computed in place with no state copy, using an X bit-flip mask, a Z phase mask with popcount parity, and a global i^(#Y) phase. Each pair (i, i⊕xmask) is visited once.

### Cited Findings
- **qsim `Sample()`:** computes `norm` in double over all amplitudes. `GenerateRandomValues` uses `std::mt19937`, `uniform_real_distribution(0, norm)`, `std::sort(rs)`, and appends a sentinel `max_value`. It then streams `csum += re*re + im*im` and emits `while (m < num_samples && rs[m] < csum) bitstrings.emplace_back(8*k + j)`. The sweep is single-threaded — [qsim lib/statespace_avx.h L374-415](https://github.com/quantumlib/qsim/blob/main/lib/statespace_avx.h), [lib/util.h L67-82](https://github.com/quantumlib/qsim/blob/main/lib/util.h)
- The qsim docs say: "Multiple samples can be generated with minimal additional cost for circuits with no intermediate measurements" — [docs/overview.md](https://github.com/quantumlib/qsim/blob/main/docs/overview.md)
- **qsim single measurement:** per-thread partial norms, then a prefix sum, a random draw, chunk selection, and in-chunk selection, then `Collapse` (section 3) — [lib/statespace.h L97-128](https://github.com/quantumlib/qsim/blob/main/lib/statespace.h)
- **Aer `sample_measure(rnds)`:** with `sample_measure_index_size_ = 10`, if the state is smaller than 2^10 each shot linearly scans the probabilities. Otherwise it computes `idxs[i]` = the sum of probabilities in each of the 2^10 blocks (OpenMP-parallel). For each shot (parallel over shots) it scans `idxs` to find the block, then scans within the block — [qubitvector.hpp L2149-2228](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qubitvector.hpp)
- **Aer `expval_pauli`:** `pauli_masks_and_phase` gives `x_mask, z_mask, num_y, x_max`. If `x_mask == 0`, it sums |a_i|² with sign `popcount(i & z_mask) & 1`. Otherwise it iterates half the space (inserting a zero at `x_max`) and pairs i with i ^ x_mask, as an OpenMP reduction with no state copy — [qubitvector.hpp L2300-2345](https://github.com/Qiskit/qiskit-aer/blob/main/src/simulators/statevector/qubitvector.hpp)
- **Qulacs `expectation_value_multi_qubit_Pauli_operator_XZ_mask`:** loops over `dim/2` indices with `basis_0 = insert_zero_to_basis_index(i, pivot_mask, pivot)` and `basis_1 = basis_0 ^ bit_flip_mask`. The sign is `popcount(basis_0 & phase_flip_mask) % 2`. It accumulates `Re(state[b0] * conj(state[b1]) * PHASE_90ROT[(global_phase_90rot_count + sign*2) % 4] * 2)` with `omp parallel for reduction(+:sum)` and no copy — [qulacs stat_ops_expectation_value.cpp L352-372](https://github.com/qulacs/qulacs/blob/main/src/csim/stat_ops_expectation_value.cpp)

### Inferences
- **Rust sampling plan:**
  1. Do one parallel pass computing per-chunk probability sums in f64. A chunk is one thread's contiguous range, or 2^10–2^16 amplitudes.
  2. Generate S uniforms and sort them, or generate them already sorted via exponential spacings to skip the sort.
  3. Each thread handles the sorted uniforms that fall in its chunk range, so a second parallel pass scans only its own chunk.

  This keeps total memory traffic at about 2 passes for any number of shots.
- Alternatives for S ≫ 2^n/…: Walker/Vose alias tables give O(1) per sample after O(2^n) setup, but need 2^n × (f32 + u32) of extra memory, which is prohibitive at n = 30–32. A binary search over block prefix sums followed by an in-block scan is a memory-cheap middle ground. No simulator source using alias tables was found (inference only).
- For Pauli sums, group terms by `x_mask`. Terms that share an `x_mask` can be evaluated in the same pass, each with its own `z_mask` parity, which cuts passes from #terms to #distinct-x-masks. This is a natural extension of the Aer/Qulacs kernels and was not seen implemented in the sources read.

### Gaps
- No source benchmarked sampling methods (sorted sweep vs block index vs alias) against each other.
- I did not check whether any simulator parallelizes the sorted-uniform sweep. qsim's is serial.
